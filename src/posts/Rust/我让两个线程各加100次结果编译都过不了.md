从 C++/Java 过来学 Rust 的，大概都经历过同一种感觉：这编译器在跟我作对。

我最近花了几周时间系统性过了一遍 Rust——Rustlings 练习题、标准库、然后一头扎进多线程。这篇不打算写成教程，网上教程够多了。我想记录的是**每个概念第一次把我拦下来的瞬间**，以及我后来是怎么想通的。

先说结论：那些让我抓狂的编译错误，最后都变成了我感谢编译器的理由。

## 起点：一段"必然正确"的代码

学线程的第二天，我写了一个自认为天经地义的程序——两个线程，各自给计数器加 100 次：

```rust
use std::thread;

fn main() {
    let mut cc = 0u32;
    let handles: Vec<_> = (0..2).map(|_| {
        thread::spawn(move || {
            for _ in 1..100 {
                cc += 1;   // 编译错误
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    println!("{}", cc);
}
```

在 C++ 里这段代码能编译，只是结果不对——数据竞争嘛，老朋友了。而 Rust 直接拒绝编译：

> error[E0382]: use of moved value: `cc`
> value moved into closure here, in previous iteration of loop

我的第一反应是去论坛搜"怎么让它编译过"，后来才意识到问错了问题。Rust 不是在刁难我，它是在告诉我：**这个程序有数据竞争，而数据竞争在 Rust 里不是运行时 bug，是编译错误。**

想让它通过，必须显式选择一种共享策略。整个 Rust 并发学习，本质上就是在回答一个问题：

> 我知道有竞争，那我到底该怎么共享这个数据？

下面是我依次找到的三个答案。

## 答案一：`Arc<AtomicU32>` —— 原子计数器

最直接的场景（简单计数）用原子类型：

```rust
use std::sync::atomic::{AtomicU32, Ordering};
use std::sync::Arc;

fn main() {
    let cc = Arc::new(AtomicU32::new(0));
    let handles: Vec<_> = (0..2).map(|_| {
        let cc = Arc::clone(&cc);
        thread::spawn(move || {
            for _ in 1..100 {
                cc.fetch_add(1, Ordering::Relaxed);
            }
        })
    }).collect();
    for h in handles { h.join().unwrap(); }
    println!("{}", cc.load(Ordering::Relaxed)); // 200，次次正确
}
```

`Arc` 解决"多线程共享所有权"，`AtomicU32` 解决"无锁的原子自增"。但真正让我失眠的是 `Ordering` 这个参数——`Relaxed` 是什么？还能怎么"放松"？

### Store Buffer：当我第一次见到 (0, 0)

我专门写了个实验来搞明白内存序（这是个经典问题，Dekker 模式）：

```rust
use std::sync::atomic::{AtomicUsize, Ordering::Relaxed};
use std::thread;

fn main() {
    let x = AtomicUsize::new(0);
    let y = AtomicUsize::new(0);
    let (r0, r1) = thread::scope(|s| {
        let a = s.spawn(|| { x.store(1, Relaxed); y.load(Relaxed) });
        let b = s.spawn(|| { y.store(1, Relaxed); x.load(Relaxed) });
        (a.join().unwrap(), b.join().unwrap())
    });
    println!("{} {}", r0, r1); // 真的会打出 0 0！
}
```

两个线程各自"先写后读"，直觉上 `(r0, r1) == (0, 0)` 不可能——总得有一个先写进去吧？但跑多几次，`0 0` 真的会出现。

原因是现代 CPU 每个核都有 **store buffer**：写操作先进本地缓冲区，延迟同步到其他核。`Relaxed` 序只保证单个变量的操作原子，完全不承诺跨变量的可见顺序。要建立"先写后读"的跨线程保证，需要 `Release`（写端）配 `Acquire`（读端），或者最简单的 `SeqCst`。

这一刻我理解了为什么 C++ 的无锁代码人人避之不及——同样的内存序问题在那边没有编译器拦你，全靠自觉。而 Rust 把 `Ordering` 做成了每个原子操作的必填参数，逼你每次都直面这个问题。

## 答案二：`Mutex` —— 互斥锁，以及"那还不如开线程吗"

对于复合数据，用 `Mutex<T>`：

```rust
use std::sync::{Arc, Mutex};

let n = Arc::new(Mutex::new(0));
// 线程里：
let mut guard = n.lock().unwrap();
*guard += 1;
drop(guard); // 作用域结束自动释放，忘了也没事
```

用锁的时候我有个从 C 带过来的老疑惑，纠结了很久：

> 多个线程竞争同一把锁，虽然保护了数据，但修改 n 的部分相当于串行了。锁那么慢，"那还不如直接 for 循环算了，还用啥 thread？"

后来想通的是：**锁的代价要放在整体工作里衡量**。线程的全部工作不可能只是 `n += 1`；如果每次修改之间有大量独立计算或 I/O，锁的开销占比就很小，并行收益远大于锁成本。如果一段"并行代码"的全部内容就是改同一个变量，那本来就不该开线程——这不是锁的问题，是我开线程的理由就是错的。

顺带一提，`Mutex` 还有个让我惊喜的设计：守卫（guard）离开作用域自动解锁，配合编译期检查，C 里那种"忘了解锁"或"锁了还去改"的事故在 Rust 里很难写出来。

## 答案三：mpsc 通道 —— 让数据流动而不是共享

Go 的口号在这里同样适用 Rust："Don't communicate by sharing memory; share memory by communicating."

```rust
use std::sync::mpsc;

fn simple_send_recv(items: Vec<String>) -> Vec<String> {
    let (tx, rx) = mpsc::channel();
    for item in items {
        let tx = tx.clone();           // 每个线程一个发送端
        thread::spawn(move || tx.send(item).unwrap());
    }
    drop(tx);                          // 关键！见下文
    rx.iter().collect()
}
```

这里有个我真实踩过的坑：**多生产者时，原始的 `tx` 必须 drop 掉**。`mpsc` 是 multiple producer single consumer，`rx.iter()` 会一直读到所有 sender 都销毁为止——克隆出去的 tx 销毁了，但原始 tx 还在手里攥着，通道永远不会关闭，程序直接卡死。加上 `drop(tx)` 就好了。

通道还有个妙用：捕获子线程的 panic。`recv()` 返回 `Err` 就说明发送端全没了（可能是 panic），比 join 的 unwrap 优雅不少。

## 回头看：线程借用栈变量为什么必须 `move`

写出开头的代码之前，我其实先写过更简单的一版：

```rust
let s = "hello";
thread::spawn(|| println!("{}", s));  // 编译不过
```

为什么闭包不能直接借用 `s`？因为 `thread::spawn` 的线程可能活得比当前函数久——如果主函数先返回了，`s` 就没了，子线程还拿着引用，悬垂指针。所以 spawn 要求闭包 `'static`：要么 `move` 把所有权转移进去，要么用 `thread::scope`：

```rust
fn scoped_slice_sum(a: &[i32], b: &[i32]) -> (i32, i32) {
    thread::scope(|s| {
        let ha = s.spawn(|| a.iter().sum::<i32>());  // 直接借用，无需 move
        let hb = s.spawn(|| b.iter().sum::<i32>());
        (ha.join().unwrap(), hb.join().unwrap())
    })
}
```

`thread::scope`（Rust 1.63+）承诺作用域结束前 join 所有子线程，所以允许借用栈上的局部变量，比 `spawn + Arc` 干净太多。做"分片求和"这种 fork-join 任务时它是首选。我一开始还在 scope 的闭包里手贱加了 `move`，后来才明白那是把切片引用拷贝进去，画蛇添足——直接借用就是 scope 的意义所在。

## Rustlings：语法之外的收获

并发之前，我是靠 Rustlings 把基础打下来的。有几个练习在我脑子里留下来了：

**`move_semantics6`**——只允许增删 `&` 符号来修复代码。这个限制逼着我画出每个值的流向：什么时候所有权转移，什么时候只是借用。做完之后"何时该用 `&`"基本成了肌肉记忆。

**`options2`**——第一次真正理解 match 是**按值消费**的：

```rust
match maybe_name {
    Some(n) => println!("Hello, {n}"),
    _ => println!("Hello, world"),
}
// maybe_name 在这里已经失效了！
```

这和 switch 完全不是一回事。不想消费原值，就用 `if let` / `while let`，或者匹配引用。`Option` + 强制穷尽 match 的组合，让我这个写过无数 NullPointerException 的人感觉非常安全。

**`errors2` ~ `errors6`**——从 `?` 运算符到自定义错误枚举。最大的观念转变是：**错误是值**。`Result<T, E>` 可以传播、转换、组合，而 `Box<dyn Error>` 适合快速原型，库代码应该定义自己的错误类型让调用方决策。

**`lifetimes1`**——卡得最久的练习。最后我的理解是：生命周期标注**不改变**任何实际的生命周期，它只是描述，供编译器检查引用不会悬空。`&'a i32` 的意思是"这个引用的存活不超过 `'a`"，仅此而已。

**`threads2`**——用 `Arc<Mutex<>>` 让多个线程更新共享的 `jobs_completed`。做完这个再回头看开头那段编译不过的代码，一切都有了答案。

## 环境与工具链上的两个小坑

**`cargo new test` 会失败**——`test` 和 Rust 内置测试库重名。顺便理解了包名、crate 名、目录名的关系。

**家目录下执行 `cargo build` 报"找不到 Cargo.toml"**——cargo 靠向上查找定位工程，这是它的机制而不是 bug。

另外我的开发环境是 Windows + WSL2 双份工具链：Windows 的 MSVC 工具链编译 PE 程序，WSL2 里的 Linux 工具链编译 ELF。两套 `~/.cargo` 互不冲突，代码放 Windows 磁盘、VSCode Remote-WSL 里编译运行，是我现在最顺的工作流。之后做操作系统训练营（oscamp）的内核实验，全靠 WSL 这套环境。

## 一个月后的复盘

回头看，Rust 的学习曲线陡，但陡的方式很特别：**困难集中在编译期**。

- C++ 里 `cc += 1` 的数据竞争：运行时偶现、难复现、上生产才炸
- Rust 里同样的代码：第一次编译就被拦下，错误信息还告诉你怎么改

被编译器毒打的这几周，实际上是在提前排掉生产环境的雷。"Fearless Concurrency" 不是口号——当你确信编译通过的程序没有数据竞争时，写多线程的心态是完全不一样的。
